# Roadmap

The curated public roadmap for ha-paneld. Shipped work lives in [CHANGELOG.md](../CHANGELOG.md). Nothing here is a dated commitment during the v0.x line — it is the direction, ordered roughly by priority within each tier.

## Planned

- **Multilingual UI rollout** — Stage 0 in 0.9.7.x introduces locale selection, fallback-safe catalogues and the Settings proof surface. Stage 1 in 0.9.8 expands coverage to guided setup and every `:8888` page. Complete the remaining product and user-guidance rollout before 0.9.9.
- **Adaptive proximity fleet validation** — validate the zero-configuration learner and deliberate-wave journey across more firmware revisions and community hardware. Compare learned health, normalized 0–100 output, and gesture acceptance without adding per-panel tuning controls.
- **More performance tooling** — v0.9.4 adds direct interaction and state-stream diagnostics, conservative cause attribution and seven-day history, while v0.9.5 adds a filtering comparison. Still planned: browser-console capture, per-card/resource attribution and clearer guided interpretation of the recorded results.
- **Central log shipping — remaining surfaces** — the core shipped in 0.8.5 (opt-in, redacted forwarding of ha-paneld's own logs to a configurable syslog/HTTP sink), 0.8.6 adds a live in-browser log viewer (Logs tab, app + system sources), and 0.9.6 adds explicit syslog TCP and UDP transports, live redacted status and an API sink preflight. Still to come: capturing the dashboard **browser console** (WebView JS console + errors, over the existing CDP path) and **shipping** the full system `logcat` to the remote sink where root allows (the local viewer already tails it).
- **Auto-brightness learning follow-ups** — the first adaptive pass now keeps a rolling seven-day ambient-light pattern on the panel, uses normal time-of-day/solar brightness as its idle baseline and reacts to short positive deviations such as artificial lighting. Remaining work is to evaluate real-room traces across seasons and hardware, then decide whether explicit manual corrections should train the curve rather than only pausing automatic control. The learned history can already be reset when a panel moves.
- **MQTT TLS — self-signed & autodiscovery** — explicit `ssl://` / `mqtts://` TLS shipped in 0.8.8 (the default trust store is used, so a **CA-signed** broker certificate validates; the port defaults to 8883). Still planned: **zero-config autodiscovery** (a TLS-first probe on 8883 that falls back to plaintext 1883 on a failed handshake), and graceful handling of the common home **self-signed** broker. That handling should be one of the following, never a silent trust-all (MITM footgun):
  - **trust-on-first-use** — pin the presented cert's fingerprint, shown in the `:8888` UI to confirm
  - a **user-supplied CA** upload for the strict path
  - a clearly-labelled **opt-in "accept self-signed / insecure"** toggle

  MQTT-over-WebSocket (`ws://` / `wss://`) is a related follow-up.
- **Boot-to-dashboard + auto-return** — reload returns to the per-panel **home dashboard** (0.8.5), and the built-in renderer adds boot-to-dashboard + an optional **idle return-to-home** (0.9). Still to extend to the Companion path: cold-start/boot and idle auto-return landing on *this panel's* dashboard rather than the Companion's user-default.
- **Installer default-app setup** — renderer-aware deploy-time flags for `install.sh` / `provision.sh` that apply the selected dashboard path as Android's home target where needed, sideline the vendor launcher and optionally set the HA Companion as the **Assist & voice input** provider on panels that use Assist. The built-in renderer already takes the home role when selected; this adds idempotent installer automation for the remaining external-app path.
- **Built-in relay control beyond the S9E** — the same `switch.<panel>_relay*` model on other panels with onboard relays, once each one's control path (GPIO / vendor node) is known.
- Daemon boot-persistence on su-only (PX30) panels, if true-off is wanted without relying on `su` at runtime.
- **On-device scheduler** — run panel actions (screen on/off, sleep/wake, reboot, reload/navigate URL) at **fixed times or repeating intervals**, configured from the HTTP UI or REST API. Runs on-device, so schedules keep working through Home Assistant or network outages (unlike an HA automation). Parity with the vendor tools' scheduled screen-on / reboot.
- **HTTP UI redesign — continued iteration** — the first cut shipped in 0.8.5 (a tabbed multi-page app with a schema-driven Configure tab and per-setting Home Assistant exposure); 0.8.6 turned Install into a full software-management hub and added a panel switcher, while later releases added screenshot-based remote taps and separate Dashboard and Reload actions. The layout, grouping and navigation are **still settling** and will keep changing over the next releases: curating the reduced "Basic" settings view, refining which values sit on which dashboard cards, and the customisable layout below.
- **Customisable info-page layout** — drag-and-drop card re-ordering plus a per-card collapse (disclosure triangle) so users can hide cards they don't care about, with the card order + collapsed state **persisted per panel**. (Card title bars were demarcated as the groundwork for this.)
- **Detect and safely repair the legacy vendor-native NSPanel Pro Zigbee watchdog defect** — firmware containing a recursive `LD_LIBRARY_PATH` assignment can eventually make every external command launched by the watchdog fail with `E2BIG`, pinning a CPU core and preventing recovery of a dead `zgateway`; the reporter confirmed this on NSPanel Pro 120 stock 3.8.0 ([#34](https://github.com/maxlyth/ha-paneld/issues/34)). Admission must require the exact vulnerable vendor-native script and assignment, distinguish NSPPT-managed and user-modified layouts, and combine file identity with guard CPU/memory and gateway health. Any explicit repair must verify a non-empty metadata-preserving backup, make exactly one idempotent change, roll back on failure, restart and verify the gateway and warn that firmware rewriting `/vendor` removes the patch. Community inspection of 4.0.12 and 4.6.0 did not find the defect.

## Stretch candidates for the initial v1.0 release

The initial v1.0 release may have room for one larger stretch direction beyond the planned reliability and provisioning work. **Fleet management** and **Voice Assistant support** are competing candidates, not commitments:

1. **Fleet management** — manage panel inventory, profiles, shared configuration and rollout state without implying that every panel is identical. The existing provisioning scripts remain the supported fleet path while this is evaluated; the earlier placeholder Fleet tab is not a promise of a v1.0 management console.
2. **Voice Assistant / Assist satellite** — add a privacy-gated panel voice path, drawing on the public Android prior art in the [Home Assistant Companion app](https://github.com/home-assistant/android) and [Ava](https://github.com/brownard/Ava), so a panel can capture an intentional request and use a Home Assistant Assist pipeline. Wake-word, push-to-talk, audio-focus, feedback and failure recovery all need a bounded design before this can be selected.

## Longer-term stretch goals

These larger directions fit a panel agent well but are not on the initial v1.0 path. They are listed to gauge interest and shape the architecture early, and lean on the same panel-as-a-first-class-local-device primitives ha-paneld is already building.

1. **Camera + microphone stream (RTSP / WebRTC), importable as an HA camera** — expose the panel's front camera and mic as an RTSP or WebRTC stream that Home Assistant ingests via its generic-camera / go2rtc / WebRTC stack, turning a wall panel into a room camera or video intercom. Needs `CAMERA` + `RECORD_AUDIO` — opt-in, privacy-gated, with an on-panel recording indicator. Overlaps with Fully Kiosk's camera/motion feature and dedicated room cameras.
2. **Push-to-talk (PTT) intercom** — press-and-hold on one panel to talk live on another room's panel over the LAN: low-latency, direct panel-to-panel, no cloud. Reuses the mic-capture + speaker-playback primitives. Overlaps with Alexa/Sonos drop-in, but local-only and across mixed hardware.
3. **Expand remote control via the web UI** — the Dashboard tab now supports screenshot-based pixel taps in Relaxed security mode. A richer control surface could add swipe/drag, keyboard input and a faster capture path, but it is not intended to become a real-time multi-touch terminal. This overlaps with Fully Kiosk remote admin and scrcpy/VNC, but could remain tightly integrated with ha-paneld's panel and security model.
4. **DLNA / UPnP media renderer** — advertise the panel as a UPnP/DLNA media renderer so Home Assistant auto-discovers it as a `media_player`. It would appear as a **separate** HA device (MQTT discovery has no media_player platform, so it can't join the panel's MQTT-discovery device), and the shipped [TTS recipe](tts.md) already covers the main announce case — so this is an interest-gauge, not a commitment.
