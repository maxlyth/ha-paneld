# Electron WF1589T (Rockchip rk3576)

Le panneau haut de gamme de la série : une unité rk3576 dotée d’un écran **10,1 pouces 1920×1200 (~226 ppp)**, de **4 Go de RAM**, d’une **LED RVB pilotable directement par l’application** (sans accès root), d’une centrale inertielle à 6 axes et des **services Google Play**, de sorte que WebView et les applications se mettent à jour automatiquement. Son firmware fournit également la propre barre de navigation d’Android. Une puce NFC est présente, mais inactive. Rétro-ingénierie effectuée sur un appareil réel (Android 14 userdebug, `adb root`).

> [!TIP]
> Most-needed facts: `userdebug` so **`adb root` just works**; the LED is the one panel that needs **no root path** (`/dev/ledjni`, world-rwx); **GMS/Play present** so **no WebView sideload** is needed; the bundled profile offers **Native navbar** mode; stock UI is **physically tiny** until you [raise the display density](#densité-daffichage--augmentez-la).

## Obtenir un accès adb + root

The WF1589T ships as a `userdebug` build with Google Play, so `adb root` works directly and `su` is present — no password, no backdoor. The LED is app-direct (below), so root is rarely needed at all.

```bash
adb root                     # userdebug → root adbd shell
adb shell su 0 id            # uid=0 → root confirmed
```

> [!CAUTION]
> The WF1589T has an OTA updater (`com.elclcd.otaupdater`) that can revert your changes. If you've enabled adb, disable it (reversible): `adb shell pm disable-user --user 0 com.elclcd.otaupdater`. See [Stop unwanted updates](../../firmware-backup-restore.md#stop-unwanted-updates).

## WebView — déjà géré par Play

The WF1589T has **Google Play**, so unlike the PX30 + TPA10 you don't sideload a WebView: update *Android System WebView* from the Play Store (or the Play WebView dev channel) and you're current. See [Updating the system WebView](README.md#mise-à-jour-du-webview-système) for the cross-panel picture.

## Barre de navigation Android native

The WF1589T firmware draws its own Back, Home and Recents bar. Its bundled profile therefore offers `Native` navbar mode, which leaves those controls to Android and draws no ha-paneld overlay or reveal strip. The capability is profile-gated rather than tied to this model in code. Other panel profiles can declare it after their firmware's navbar has been verified. Fullscreen renderer settings and Android dashboard lock can still hide the system bar.

## Densité d’affichage — augmentez-la

À la densité logique d’usine/de base (160 dpi), Android effectue le rendu à environ 1 dp ≈ 1 px ; les boutons, le texte et les cartes du tableau de bord sont donc **physiquement minuscules et difficiles à toucher**. La valeur de base est la référence de réinitialisation de la mise en page d’Android, et non la densité physique d’environ 226 ppp du panneau. Le préréglage **optimisé pour HA** de ha-paneld utilise 212 dpi comme point de départ vérifié ; adaptez-le à la pièce et au tableau de bord selon vos préférences :

```sh
adb shell wm density 212        # ha-paneld starting point; `wm density reset` restores the 160-dpi base
```

À 212 dpi, la surface effective est d’environ 1449×906 dp. Augmenter la valeur agrandit l’interface tactile et affiche moins de contenu du tableau de bord ; la diminuer produit l’effet inverse.

## LED — `/dev/ledjni` (accès direct par l’application, sans root)

`/sys/class/leds` has no RGB node (only `mmc1::`). The front RGB LED is driven through a character device that is world-rwx and labelled `device` (app-accessible under SELinux), so a normal app drives it **without root or a helper daemon**. This is the one panel class where the LED needs no root path.

ha-paneld uses this via `Rk3576LedController` (the LED entity is published only where `/dev/ledjni` opens).

The factory `com.gulukai.pwmlightdemo` package also opens this device. Its boot-started foreground service continuously cycles the LED through seven colours, overwriting commands from ha-paneld and making Home Assistant's last commanded state differ from the physical LED. The device protocol has no state read-back, so two applications cannot share truthful control. The WF1589T profile therefore marks this demo as recommended in the **Vendor packages** UI, where disabling it remains a deliberate reversible action.

<details>
<summary>Nœud `/dev/ledjni` et protocole ioctl</summary>

```text
/dev/ledjni   crwxrwxrwx  system system  u:object_r:device:s0
```

Le protocole ioctl (rétro-ingénierie en salle blanche à partir de l’exemple du fournisseur, aucun blob propriétaire inclus — voir [`app/src/main/cpp/led_jni.c`](../../../app/src/main/cpp/led_jni.c)) :

```c
int fd = open("/dev/ledjni", O_RDONLY | O_NOCTTY);
ioctl(fd, 0xa1, R);   // red,   0..15
ioctl(fd, 0xa2, G);   // green, 0..15
ioctl(fd, 0xa3, B);   // blue,  0..15
ioctl(fd, 0x99, 0);   // off
close(fd);
```

</details>

## Capteurs — centrale inertielle à 6 axes (via le service Android `SensorManager`)

Fait inhabituel pour un panneau mural, le WF1589T expose un ensemble complet de capteurs de mouvement via l’API `SensorManager` standard (sans root) : `accelerometer`, `gyroscope`, `gravity`, `linear_acceleration`, `game_rotation_vector`. Puces sous-jacentes : Kionix **KXTJ9** + Bosch **BMA2xx** (accéléromètre). Aucun `TYPE_LIGHT`/`TYPE_PROXIMITY` n’est exposé (aucun n’est installé).

Aucun capteur de luminosité ambiante, de proximité, de température ou d’humidité n’est lié sur cette carte (contrairement au [TPA10](tpa10.md), qui possède les quatre). La détection de présence repose ici uniquement sur le mouvement, via la centrale inertielle.

## Caméra

GalaxyCore **GC05A2** (I2C `4-0037` dans le tableau ci-dessus), un capteur de 2592x1944. Android signale une caméra au niveau matériel `LIMITED`, `BACKWARD_COMPATIBLE` uniquement, `Facing: Front`, sans flash ni autofocus, par l’intermédiaire du fournisseur `internal/0-1`. Un second fournisseur `external/0-0` est présent, sans aucun périphérique associé, et le panneau déclare `android.hardware.camera.external`.

La résolution 1280x720 est proposée dans les trois formats : `IMPLEMENTATION_DEFINED`, `YUV_420_888` et `BLOB`. La HAL annonce un blocage d’une image pour une capture `BLOB` 720p à 30 i/s, mais ha-paneld capture en `YUV_420_888` et effectue la compression JPEG de manière logicielle ; cette valeur ne mesure donc pas le coût d’un instantané pour l’application. `android.control.aeAvailableTargetFpsRanges` ne propose que `[15 30]` et `[30 30]` : il n’existe aucun mode capteur verrouillé à 15 i/s ; un flux à 15 i/s résulte donc du cadencement de l’encodeur et non d’une demande adressée au capteur.

L’encodeur matériel H.264 est `c2.rk.avc.encoder`, fourni par la HAL Codec2 (`android.hardware.media.c2@1.1-service` ; aucun processus OMX `media.codec` n’existe sur ce panneau). Il possède `OMX.rk.video_encoder.avc` comme alias : une sélection par nom trouve donc *quelque chose* à la fois sur ce panneau et sur le TPA10, mais il s’agit de composants différents, situés de part et d’autre de la transition d’OMX vers Codec2, dont il ne faut pas supposer que le comportement est identique. Il déclare une plage de `176x144` à `4096x2160` avec un alignement de `2x2`, une plage de débit annoncée de 1 bit/s à 20 Mbit/s et 32 instances simultanées. Contrairement au TPA10, ce panneau possède également un encodeur matériel HEVC, `c2.rk.hevc.encoder`, que ha-paneld n’utilise pas actuellement.

Un panneau qui affiche des cartes de caméra n’est pas inactif : sur le tableau de bord du parc mesuré, ha-paneld maintenait deux instances `c2.rk.avc.decoder` actives ; une session d’encodage entre donc en concurrence avec le décodage existant sur le même VPU Rockchip.

ha-paneld includes an **experimental camera-serving feature that is off by default**. It is enabled per panel by the **Camera** switch on the Camera card in Configure, which appears because this panel has a camera - here because the device profile declares `hardware.camera`, though a board whose profile says nothing offers the card too whenever Android enumerates a camera (see [enabling the camera on a panel whose profile does not declare one](../../profiles/unofficial/README.md#enabling-the-camera-on-a-panel-whose-profile-does-not-declare-one)), alongside **Resolution**, **Frame rate** and **Bitrate** (720p / 15 fps / 2000 kbps) and an **Exposure** bias in stops for a camera that reads the room darker or brighter than it looks. Those three are what a stream gets when its URL asks for nothing, and a stream URL can override any of them in either direction; they are defaults, not ceilings. Several viewers share one encode session, bound by the first one to connect, so a second viewer costs packetisation and network rather than a second encode. With the switch on it serves a video-only H.264 stream at `rtsp://<panel>:8554/live` and a still at `GET /api/v1/camera/snapshot.jpg`. Enabling the switch from Home Assistant asks for approval on the panel first, in every security mode. The RTSP URL is intended for Home Assistant Generic Camera, go2rtc and Frigate ingestion. Whenever the camera is open the panel draws its own red indicator that page content cannot cover, and if that indicator cannot be drawn the camera does not open. It flashes about once a second when the camera opens and backs off over a couple of minutes to a flash about once a minute; the half-second flash never gets shorter or fades away, settling at 62% opacity as it becomes rarer. A new stream, a recovery after a fault or the screen coming back on returns it to a flash every second, and no setting turns it off or changes the schedule. See [`GET /api/v1/status`](../../api.md) for the `camera` object that reports the encoder, the delivered frame rate and bitrate, and any fault.

> [!WARNING]
> Do not put a Home Assistant camera card for **this** panel on **this** panel's own dashboard. The panel would decode its own encode in a loop, on the same video engine, for no benefit.


## NFC — présent, mais non intégré à Android

An **NXP NFC controller** is bound at `i2c-7 0x28` (`nxpnfc` driver) with a `/dev/nxpnfc` node (`crw------- root root`), yet `pm list features` does **not** report `android.hardware.nfc` — the Android NFC service/HAL is not enabled in this firmware. So the silicon exists but is inert to apps as shipped; using it would require an NFC HAL + the NfcService, or talking to `/dev/nxpnfc` directly as root. Present but unused by ha-paneld.

## Résumé du modèle d’accès

- **LED**: app-direct (`/dev/ledjni`) — no root, no daemon.
- **Centrale inertielle** : accès direct par l’application (`SensorManager`).
- **NFC**: present (NXP) but Android-NFC disabled; root-only as shipped.
- **Navigation** : barre de navigation propre à Android via le mode `Native` activé par le profil.
- **Luminosité de l’écran / veille / navigation / synthèse vocale** : voies Android standard (comme sur n’importe quel panneau).
