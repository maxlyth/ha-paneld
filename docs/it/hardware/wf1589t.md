# Electron WF1589T (Rockchip rk3576)

Il pannello di fascia alta della serie: un'unità rk3576 da **10,1" 1920×1200 (~226 ppi)** con **4 GB di RAM**, un **LED RGB controllabile direttamente dall'app** (senza necessità di root), un'IMU a 6 assi e i **servizi Google Play**, grazie ai quali WebView e le app si aggiornano autonomamente. Il firmware fornisce anche la barra di navigazione nativa di Android. Il chip NFC è presente ma inattivo. Sottoposto a reverse engineering su un'unità reale (Android 14 userdebug, `adb root`).

> [!TIP]
> Most-needed facts: `userdebug` so **`adb root` just works**; the LED is the one panel that needs **no root path** (`/dev/ledjni`, world-rwx); **GMS/Play present** so **no WebView sideload** is needed; the bundled profile offers **Native navbar** mode; stock UI is **physically tiny** until you [raise the display density](#densità-dello-schermo-aumentala).

## Ottenere accesso adb + root

The WF1589T ships as a `userdebug` build with Google Play, so `adb root` works directly and `su` is present — no password, no backdoor. The LED is app-direct (below), so root is rarely needed at all.

```bash
adb root                     # userdebug → root adbd shell
adb shell su 0 id            # uid=0 → root confirmed
```

> [!CAUTION]
> The WF1589T has an OTA updater (`com.elclcd.otaupdater`) that can revert your changes. If you've enabled adb, disable it (reversible): `adb shell pm disable-user --user 0 com.elclcd.otaupdater`. See [Stop unwanted updates](../../firmware-backup-restore.md#stop-unwanted-updates).

## WebView: già gestito da Play

The WF1589T has **Google Play**, so unlike the PX30 + TPA10 you don't sideload a WebView: update *Android System WebView* from the Play Store (or the Play WebView dev channel) and you're current. See [Updating the system WebView](README.md#aggiornamento-della-webview-di-sistema) for the cross-panel picture.

## Barra di navigazione Android nativa

The WF1589T firmware draws its own Back, Home and Recents bar. Its bundled profile therefore offers `Native` navbar mode, which leaves those controls to Android and draws no ha-paneld overlay or reveal strip. The capability is profile-gated rather than tied to this model in code. Other panel profiles can declare it after their firmware's navbar has been verified. Fullscreen renderer settings and Android dashboard lock can still hide the system bar.

## Densità dello schermo: aumentala

Alla densità logica di fabbrica/base (160 dpi), Android esegue il rendering a circa 1 dp ≈ 1 px, quindi pulsanti, testo e schede dashboard risultano **fisicamente piccoli e difficili da toccare**. Il valore di base è il riferimento al ripristino del layout di Android, non i ~226 PPI fisici del pannello. La preimpostazione **ottimizzata per HA** di ha-paneld utilizza 212 dpi come punto di partenza verificato; regolalo a tuo gusto per la tua stanza e il tuo cruscotto:

```sh
adb shell wm density 212        # ha-paneld starting point; `wm density reset` restores the 160-dpi base
```

A 212 dpi l'area utile effettiva è di circa 1449×906 dp. Aumentando il valore si ingrandisce l'interfaccia touch e si visualizzano meno contenuti della dashboard; diminuendolo avviene il contrario.

## LED: `/dev/ledjni` (diretto dall'app, senza root)

`/sys/class/leds` has no RGB node (only `mmc1::`). The front RGB LED is driven through a character device that is world-rwx and labelled `device` (app-accessible under SELinux), so a normal app drives it **without root or a helper daemon**. This is the one panel class where the LED needs no root path.

ha-paneld uses this via `Rk3576LedController` (the LED entity is published only where `/dev/ledjni` opens).

The factory `com.gulukai.pwmlightdemo` package also opens this device. Its boot-started foreground service continuously cycles the LED through seven colours, overwriting commands from ha-paneld and making Home Assistant's last commanded state differ from the physical LED. The device protocol has no state read-back, so two applications cannot share truthful control. The WF1589T profile therefore marks this demo as recommended in the **Vendor packages** UI, where disabling it remains a deliberate reversible action.

<details>
<summary>Nodo `/dev/ledjni` + protocollo ioctl</summary>

```text
/dev/ledjni   crwxrwxrwx  system system  u:object_r:device:s0
```

Il protocollo ioctl (ricostruito tramite reverse engineering clean-room dal campione del produttore, senza includere blob proprietari — vedi [`app/src/main/cpp/led_jni.c`](../../../app/src/main/cpp/led_jni.c)):

```c
int fd = open("/dev/ledjni", O_RDONLY | O_NOCTTY);
ioctl(fd, 0xa1, R);   // red,   0..15
ioctl(fd, 0xa2, G);   // green, 0..15
ioctl(fd, 0xa3, B);   // blue,  0..15
ioctl(fd, 0x99, 0);   // off
close(fd);
```

## Sensori: IMU a 6 assi (tramite Android `SensorManager`)

Caso insolito per un pannello a parete, il WF1589T espone un set completo di sensori di movimento tramite l'API standard `SensorManager` (senza root): `accelerometer`, `gyroscope`, `gravity`, `linear_acceleration`, `game_rotation_vector`. Chip sottostanti: Kionix **KXTJ9** + Bosch **BMA2xx** (accelerometri). Non vengono esposti `TYPE_LIGHT` o `TYPE_PROXIMITY` perché i relativi sensori non sono installati.

Su questa scheda non è collegato alcun sensore di luce ambientale, prossimità, temperatura o umidità (a differenza del [TPA10](tpa10.md), che li ha tutti e quattro). Il rilevamento della presenza in questo caso è solo movimento, tramite l'IMU.

## Fotocamera

GalaxyCore **GC05A2** (i2c `4-0037` nella tabella sopra), un sensore 2592x1944. Android segnala una fotocamera a livello hardware `LIMITED`, solo `BACKWARD_COMPATIBLE`, `Facing: Front`, senza flash e senza messa a fuoco automatica, tramite il provider `internal/0-1`. Un secondo provider `external/0-0` è presente senza dispositivi collegati e il pannello dichiara `android.hardware.camera.external`.

1280x720 è disponibile in tutti e tre i formati: `IMPLEMENTATION_DEFINED`, `YUV_420_888` e `BLOB`. L'HAL dichiara uno stallo di un fotogramma per un'acquisizione 720p in formato `BLOB` a 30 fps, ma ha-paneld acquisisce in `YUV_420_888` ed esegue la compressione JPEG via software, quindi tale valore non misura il costo delle istantanee dell'app. `android.control.aeAvailableTargetFpsRanges` offre solo `[15 30]` e `[30 30]`: non esiste una modalità del sensore bloccata a 15 fps, perciò un flusso a 15 fps si ottiene regolando la cadenza dell'encoder, non richiedendola al sensore.

Il codificatore hardware H.264 è `c2.rk.avc.encoder`, gestito dall'HAL Codec2 (`android.hardware.media.c2@1.1-service`; su questo pannello non è presente alcun processo OMX `media.codec`). Espone `OMX.rk.video_encoder.avc` come alias, quindi la selezione basata sul nome trova *qualcosa* sia su questo pannello sia sul TPA10; si tratta però di componenti diversi, situati sui lati opposti della transizione da OMX a Codec2, e non si deve presumere che si comportino allo stesso modo. Dichiara risoluzioni da `176x144` a `4096x2160` con allineamento `2x2`, un intervallo di bitrate dichiarato da 1 bps a 20 Mbps e 32 istanze simultanee. A differenza del TPA10, questo pannello dispone anche di un codificatore HEVC hardware, `c2.rk.hevc.encoder`, che ha-paneld attualmente non utilizza.

Un pannello che mostra schede della fotocamera non è inattivo: nella dashboard della flotta sottoposta a misurazione, ha-paneld manteneva attive due istanze `c2.rk.avc.decoder`, quindi una sessione di codifica compete con il carico di decodifica già presente sulla stessa VPU Rockchip.

ha-paneld includes an **experimental camera-serving feature that is off by default**. It is enabled per panel by the **Camera** switch on the Camera card in Configure, which appears because this panel has a camera - here because the device profile declares `hardware.camera`, though a board whose profile says nothing offers the card too whenever Android enumerates a camera (see [enabling the camera on a panel whose profile does not declare one](../../profiles/unofficial/README.md#enabling-the-camera-on-a-panel-whose-profile-does-not-declare-one)), alongside **Resolution**, **Frame rate** and **Bitrate** (720p / 15 fps / 2000 kbps) and an **Exposure** bias in stops for a camera that reads the room darker or brighter than it looks. Those three are what a stream gets when its URL asks for nothing, and a stream URL can override any of them in either direction; they are defaults, not ceilings. Several viewers share one encode session, bound by the first one to connect, so a second viewer costs packetisation and network rather than a second encode. With the switch on it serves a video-only H.264 stream at `rtsp://<panel>:8554/live` and a still at `GET /api/v1/camera/snapshot.jpg`. Enabling the switch from Home Assistant asks for approval on the panel first, in every security mode. The RTSP URL is intended for Home Assistant Generic Camera, go2rtc and Frigate ingestion. Whenever the camera is open the panel draws its own red indicator that page content cannot cover, and if that indicator cannot be drawn the camera does not open. It flashes about once a second when the camera opens and backs off over a couple of minutes to a flash about once a minute; the half-second flash never gets shorter or fades away, settling at 62% opacity as it becomes rarer. A new stream, a recovery after a fault or the screen coming back on returns it to a flash every second, and no setting turns it off or changes the schedule. See [`GET /api/v1/status`](../../api.md) for the `camera` object that reports the encoder, the delivered frame rate and bitrate, and any fault.

> [!WARNING]
> Do not put a Home Assistant camera card for **this** panel on **this** panel's own dashboard. The panel would decode its own encode in a loop, on the same video engine, for no benefit.


## NFC: presente ma non collegato ad Android

An **NXP NFC controller** is bound at `i2c-7 0x28` (`nxpnfc` driver) with a `/dev/nxpnfc` node (`crw------- root root`), yet `pm list features` does **not** report `android.hardware.nfc` — the Android NFC service/HAL is not enabled in this firmware. So the silicon exists but is inert to apps as shipped; using it would require an NFC HAL + the NfcService, or talking to `/dev/nxpnfc` directly as root. Present but unused by ha-paneld.

## Riepilogo del modello di accesso

- **LED**: app-direct (`/dev/ledjni`) — no root, no daemon.
- **IMU**: app-direct (`SensorManager`).
- **NFC**: present (NXP) but Android-NFC disabled; root-only as shipped.
- **Navigazione**: barra di navigazione di Android tramite la modalità `Native` controllata dal profilo.
- **Luminosità schermo / sospensione / navigazione / TTS**: percorsi Android standard (come su qualsiasi pannello).
