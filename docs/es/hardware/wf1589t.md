# Electron WF1589T (Rockchip rk3576)

El panel de gama alta del conjunto: una unidad rk3576 con una **pantalla de 10,1 pulgadas y 1920×1200 (~226 ppp)**, **4 GB de RAM**, un **LED RGB controlable directamente desde la aplicación** (sin necesidad de root), una IMU de 6 ejes y **servicios de Google Play**, por lo que WebView y las aplicaciones se actualizan por sí solos. Su firmware también proporciona la barra de navegación propia de Android. El chip NFC está presente, pero inactivo. Se realizó ingeniería inversa sobre una unidad real (Android 14 userdebug, `adb root`).

> [!TIP]
> Most-needed facts: `userdebug` so **`adb root` just works**; the LED is the one panel that needs **no root path** (`/dev/ledjni`, world-rwx); **GMS/Play present** so **no WebView sideload** is needed; the bundled profile offers **Native navbar** mode; stock UI is **physically tiny** until you [raise the display density](#densidad-de-pantalla-auméntela).

## Obtener acceso adb y root

The WF1589T ships as a `userdebug` build with Google Play, so `adb root` works directly and `su` is present — no password, no backdoor. The LED is app-direct (below), so root is rarely needed at all.

```bash
adb root                     # userdebug → root adbd shell
adb shell su 0 id            # uid=0 → root confirmed
```

> [!CAUTION]
> The WF1589T has an OTA updater (`com.elclcd.otaupdater`) that can revert your changes. If you've enabled adb, disable it (reversible): `adb shell pm disable-user --user 0 com.elclcd.otaupdater`. See [Stop unwanted updates](../../firmware-backup-restore.md#stop-unwanted-updates).

## WebView: ya gestionado por Play

The WF1589T has **Google Play**, so unlike the PX30 + TPA10 you don't sideload a WebView: update *Android System WebView* from the Play Store (or the Play WebView dev channel) and you're current. See [Updating the system WebView](README.md#actualización-del-webview-del-sistema) for the cross-panel picture.

## Barra de navegación nativa de Android

The WF1589T firmware draws its own Back, Home and Recents bar. Its bundled profile therefore offers `Native` navbar mode, which leaves those controls to Android and draws no ha-paneld overlay or reveal strip. The capability is profile-gated rather than tied to this model in code. Other panel profiles can declare it after their firmware's navbar has been verified. Fullscreen renderer settings and Android dashboard lock can still hide the system bar.

## Densidad de pantalla: auméntela

Con la densidad lógica de fábrica/base (160 dpi), Android representa aproximadamente 1 dp ≈ 1 px, por lo que los botones, el texto y las tarjetas del panel resultan **físicamente diminutos y difíciles de tocar**. El valor base es la referencia de Android para restablecer el diseño, no los ~226 PPI físicos del panel. El ajuste preestablecido **Optimizado para HA** de ha-paneld usa 212 dpi como punto de partida verificado; ajústelo a su gusto para la habitación y el panel de control:

```sh
adb shell wm density 212        # ha-paneld starting point; `wm density reset` restores the 160-dpi base
```

A 212 dpi, el lienzo efectivo es de aproximadamente 1449×906 dp. Al aumentar el valor, la interfaz táctil se amplía y muestra menos contenido del panel de control; al reducirlo ocurre lo contrario.

## LED: `/dev/ledjni` (control directo desde la aplicación, sin root)

`/sys/class/leds` has no RGB node (only `mmc1::`). The front RGB LED is driven through a character device that is world-rwx and labelled `device` (app-accessible under SELinux), so a normal app drives it **without root or a helper daemon**. This is the one panel class where the LED needs no root path.

ha-paneld uses this via `Rk3576LedController` (the LED entity is published only where `/dev/ledjni` opens).

The factory `com.gulukai.pwmlightdemo` package also opens this device. Its boot-started foreground service continuously cycles the LED through seven colours, overwriting commands from ha-paneld and making Home Assistant's last commanded state differ from the physical LED. The device protocol has no state read-back, so two applications cannot share truthful control. The WF1589T profile therefore marks this demo as recommended in the **Vendor packages** UI, where disabling it remains a deliberate reversible action.

<details>
<summary>Nodo `/dev/ledjni` y protocolo ioctl</summary>

```text
/dev/ledjni   crwxrwxrwx  system system  u:object_r:device:s0
```

El protocolo ioctl (obtenido mediante ingeniería inversa de sala limpia a partir del ejemplo del fabricante; no se incluye ningún blob del fabricante; consulte [`app/src/main/cpp/led_jni.c`](../../../app/src/main/cpp/led_jni.c)):

```c
int fd = open("/dev/ledjni", O_RDONLY | O_NOCTTY);
ioctl(fd, 0xa1, R);   // red,   0..15
ioctl(fd, 0xa2, G);   // green, 0..15
ioctl(fd, 0xa3, B);   // blue,  0..15
ioctl(fd, 0x99, 0);   // off
close(fd);
```

</details>

## Sensores: IMU de 6 ejes (mediante `SensorManager` de Android)

Algo poco habitual en un panel de pared es que el WF1589T exponga un conjunto completo de sensores de movimiento mediante el `SensorManager` estándar (sin root): `accelerometer`, `gyroscope`, `gravity`, `linear_acceleration` y `game_rotation_vector`. Chips subyacentes: Kionix **KXTJ9** y Bosch **BMA2xx** (acelerómetro). No se exponen `TYPE_LIGHT` ni `TYPE_PROXIMITY` (no están instalados).

En esta placa no está vinculado ningún sensor de luz ambiental, proximidad, temperatura ni humedad (a diferencia del [TPA10](tpa10.md), que cuenta con los cuatro). Aquí, la detección de presencia se basa únicamente en el movimiento, mediante la IMU.

## Cámara

GalaxyCore **GC05A2** (i2c `4-0037` en la tabla anterior), un sensor de 2592×1944. Android informa de una cámara con nivel de hardware `LIMITED`, solo `BACKWARD_COMPATIBLE`, `Facing: Front`, sin flash ni enfoque automático, mediante el proveedor `internal/0-1`. Hay un segundo proveedor `external/0-0` sin dispositivos conectados, y el panel declara `android.hardware.camera.external`.

1280×720 se ofrece en los tres formatos: `IMPLEMENTATION_DEFINED`, `YUV_420_888` y `BLOB`. La HAL anuncia una pausa equivalente a un fotograma para una captura `BLOB` a 720p y 30 fps, pero ha-paneld captura `YUV_420_888` y realiza la compresión JPEG por software, por lo que esa cifra no mide el coste de generar una instantánea en la aplicación. `android.control.aeAvailableTargetFpsRanges` solo ofrece `[15 30]` y `[30 30]`: no existe un modo del sensor fijado en 15 fps, por lo que una transmisión a 15 fps se obtiene controlando la cadencia del codificador, no solicitando al sensor que funcione a esa frecuencia.

El codificador H.264 por hardware es `c2.rk.avc.encoder`, servido por la HAL Codec2 (`android.hardware.media.c2@1.1-service`; no hay ningún proceso OMX `media.codec` en este panel). Incluye `OMX.rk.video_encoder.avc` como alias, por lo que la selección por nombre encuentra *algo* tanto en este panel como en el TPA10, pero son componentes distintos en lados opuestos de la transición de OMX a Codec2 y no debe suponerse que se comporten igual. Declara de `176x144` a `4096x2160` con alineación `2x2`, un intervalo de tasa de bits informado de 1 bps a 20 Mbps y 32 instancias simultáneas. A diferencia del TPA10, este panel también tiene un codificador HEVC por hardware, `c2.rk.hevc.encoder`, que ha-paneld no utiliza actualmente.

Un panel que muestra tarjetas de cámara no está inactivo: en el panel de control de la flota usado para las mediciones, ha-paneld mantenía dos instancias activas de `c2.rk.avc.decoder`, por lo que una sesión de codificación compite con el trabajo de decodificación existente en la misma VPU Rockchip.

ha-paneld includes an **experimental camera-serving feature that is off by default**. It is enabled per panel by the **Camera** switch on the Camera card in Configure, which appears because this panel has a camera - here because the device profile declares `hardware.camera`, though a board whose profile says nothing offers the card too whenever Android enumerates a camera (see [enabling the camera on a panel whose profile does not declare one](../../profiles/unofficial/README.md#enabling-the-camera-on-a-panel-whose-profile-does-not-declare-one)), alongside **Resolution**, **Frame rate** and **Bitrate** (720p / 15 fps / 2000 kbps) and an **Exposure** bias in stops for a camera that reads the room darker or brighter than it looks. Those three are what a stream gets when its URL asks for nothing, and a stream URL can override any of them in either direction; they are defaults, not ceilings. Several viewers share one encode session, bound by the first one to connect, so a second viewer costs packetisation and network rather than a second encode. With the switch on it serves a video-only H.264 stream at `rtsp://<panel>:8554/live` and a still at `GET /api/v1/camera/snapshot.jpg`. Enabling the switch from Home Assistant asks for approval on the panel first, in every security mode. The RTSP URL is intended for Home Assistant Generic Camera, go2rtc and Frigate ingestion. Whenever the camera is open the panel draws its own red indicator that page content cannot cover, and if that indicator cannot be drawn the camera does not open. It flashes about once a second when the camera opens and backs off over a couple of minutes to a flash about once a minute; the half-second flash never gets shorter or fades away, settling at 62% opacity as it becomes rarer. A new stream, a recovery after a fault or the screen coming back on returns it to a flash every second, and no setting turns it off or changes the schedule. See [`GET /api/v1/status`](../../api.md) for the `camera` object that reports the encoder, the delivered frame rate and bitrate, and any fault.

> [!WARNING]
> Do not put a Home Assistant camera card for **this** panel on **this** panel's own dashboard. The panel would decode its own encode in a loop, on the same video engine, for no benefit.


## NFC: presente, pero no integrado en Android

An **NXP NFC controller** is bound at `i2c-7 0x28` (`nxpnfc` driver) with a `/dev/nxpnfc` node (`crw------- root root`), yet `pm list features` does **not** report `android.hardware.nfc` — the Android NFC service/HAL is not enabled in this firmware. So the silicon exists but is inert to apps as shipped; using it would require an NFC HAL + the NfcService, or talking to `/dev/nxpnfc` directly as root. Present but unused by ha-paneld.

## Resumen del modelo de acceso

- **LED**: app-direct (`/dev/ledjni`) — no root, no daemon.
- **IMU**: acceso directo desde la aplicación (`SensorManager`).
- **NFC**: present (NXP) but Android-NFC disabled; root-only as shipped.
- **Navegación**: barra de navegación propia de Android mediante el modo `Native`, habilitado según el perfil.
- **Brillo de pantalla / suspensión / navegación / TTS**: rutas estándar de Android (como en cualquier panel).
