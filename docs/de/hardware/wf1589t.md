# Electron WF1589T (Rockchip rk3576)

Das Spitzenmodell der Reihe: ein rk3576-Panel mit **10,1 Zoll, 1920×1200 (~226 ppi)**, **4 GB RAM**, einer **direkt aus der App ansteuerbaren RGB-LED** (kein Root-Zugriff erforderlich), einer 6-Achsen-IMU und **Google-Play-Diensten**, sodass sich WebView und Apps selbst aktualisieren. Die Firmware stellt außerdem Androids eigene Navigationsleiste bereit. Der NFC-Chip ist vorhanden, aber inaktiv. An einem realen Gerät rückentwickelt (Android 14 userdebug, `adb root`).

> [!TIP]
> Most-needed facts: `userdebug` so **`adb root` just works**; the LED is the one panel that needs **no root path** (`/dev/ledjni`, world-rwx); **GMS/Play present** so **no WebView sideload** is needed; the bundled profile offers **Native navbar** mode; stock UI is **physically tiny** until you [raise the display density](#anzeigedichte--erhöhen).

## adb- und Root-Zugriff erlangen

The WF1589T ships as a `userdebug` build with Google Play, so `adb root` works directly and `su` is present — no password, no backdoor. The LED is app-direct (below), so root is rarely needed at all.

```bash
adb root                     # userdebug → root adbd shell
adb shell su 0 id            # uid=0 → root confirmed
```

> [!CAUTION]
> The WF1589T has an OTA updater (`com.elclcd.otaupdater`) that can revert your changes. If you've enabled adb, disable it (reversible): `adb shell pm disable-user --user 0 com.elclcd.otaupdater`. See [Stop unwanted updates](../../firmware-backup-restore.md#stop-unwanted-updates).

## WebView — bereits von Play verwaltet

The WF1589T has **Google Play**, so unlike the PX30 + TPA10 you don't sideload a WebView: update *Android System WebView* from the Play Store (or the Play WebView dev channel) and you're current. See [Updating the system WebView](README.md#system-webview-aktualisieren) for the cross-panel picture.

## Native Android-Navigationsleiste

The WF1589T firmware draws its own Back, Home and Recents bar. Its bundled profile therefore offers `Native` navbar mode, which leaves those controls to Android and draws no ha-paneld overlay or reveal strip. The capability is profile-gated rather than tied to this model in code. Other panel profiles can declare it after their firmware's navbar has been verified. Fullscreen renderer settings and Android dashboard lock can still hide the system bar.

## Anzeigedichte — erhöhen

Bei der werkseitigen/logischen Basisdichte (160 dpi) rendert Android ungefähr mit 1 dp ≈ 1 px. Dadurch erscheinen Schaltflächen, Text und Dashboard-Karten **physisch winzig und sind schwer zu bedienen**. Der Basiswert ist Androids Referenzwert zum Zurücksetzen des Layouts und nicht die physische Pixeldichte des Panels von ~226 ppi. Die Voreinstellung **HA-optimiert** von ha-paneld verwendet 212 dpi als verifizierten Ausgangspunkt; passen Sie den Wert nach Belieben an Raum und Dashboard an:

```sh
adb shell wm density 212        # ha-paneld starting point; `wm density reset` restores the 160-dpi base
```

Bei 212 dpi beträgt die effektive Arbeitsfläche ungefähr 1449×906 dp. Ein höherer Wert vergrößert die Touch-Bedienoberfläche und zeigt weniger Dashboard-Inhalt; ein niedrigerer Wert bewirkt das Gegenteil.

## LED — `/dev/ledjni` (direkt aus der App, kein Root-Zugriff)

`/sys/class/leds` has no RGB node (only `mmc1::`). The front RGB LED is driven through a character device that is world-rwx and labelled `device` (app-accessible under SELinux), so a normal app drives it **without root or a helper daemon**. This is the one panel class where the LED needs no root path.

ha-paneld uses this via `Rk3576LedController` (the LED entity is published only where `/dev/ledjni` opens).

The factory `com.gulukai.pwmlightdemo` package also opens this device. Its boot-started foreground service continuously cycles the LED through seven colours, overwriting commands from ha-paneld and making Home Assistant's last commanded state differ from the physical LED. The device protocol has no state read-back, so two applications cannot share truthful control. The WF1589T profile therefore marks this demo as recommended in the **Vendor packages** UI, where disabling it remains a deliberate reversible action.

<details>
<summary>Knoten `/dev/ledjni` + ioctl-Protokoll</summary>

```text
/dev/ledjni   crwxrwxrwx  system system  u:object_r:device:s0
```

Das ioctl-Protokoll (anhand des Herstellerbeispiels in einer Clean-Room-Analyse rückentwickelt; kein Hersteller-Blob enthalten — siehe [`app/src/main/cpp/led_jni.c`](../../../app/src/main/cpp/led_jni.c)):

```c
int fd = open("/dev/ledjni", O_RDONLY | O_NOCTTY);
ioctl(fd, 0xa1, R);   // red,   0..15
ioctl(fd, 0xa2, G);   // green, 0..15
ioctl(fd, 0xa3, B);   // blue,  0..15
ioctl(fd, 0x99, 0);   // off
close(fd);
```

</details>

## Sensoren — 6-Achsen-IMU (über Androids `SensorManager`)

Für ein Wandpanel ungewöhnlich stellt das WF1589T über den standardmäßigen `SensorManager` eine vollständige Bewegungssensorik bereit (kein Root-Zugriff): `accelerometer`, `gyroscope`, `gravity`, `linear_acceleration`, `game_rotation_vector`. Zugrunde liegende Chips: Kionix **KXTJ9** + Bosch **BMA2xx** (Beschleunigung). `TYPE_LIGHT`/`TYPE_PROXIMITY` wird nicht bereitgestellt (nicht verbaut).

Auf dieser Platine ist kein Umgebungslicht-, Näherungs-, Temperatur- oder Feuchtigkeitssensor angebunden (anders als beim [TPA10](tpa10.md), das alle vier besitzt). Die Anwesenheitserkennung erfolgt hier ausschließlich über Bewegung mithilfe der IMU.

## Kamera

GalaxyCore **GC05A2** (I²C `4-0037` in der obigen Tabelle), ein Sensor mit 2592x1944 Pixeln. Android meldet eine Kamera mit Hardware-Level `LIMITED`, ausschließlich `BACKWARD_COMPATIBLE`, `Facing: Front`, ohne Blitz und ohne Autofokus, über den `internal/0-1`-Provider. Ein zweiter `external/0-0`-Provider ist vorhanden, aber mit keinem Gerät verbunden; außerdem deklariert das Panel `android.hardware.camera.external`.

1280x720 wird in allen drei Formaten angeboten: `IMPLEMENTATION_DEFINED`, `YUV_420_888` und `BLOB`. Die HAL gibt für eine 720p-Aufnahme als `BLOB` bei 30 fps eine Verzögerung von einem Frame an. ha-paneld erfasst jedoch `YUV_420_888` und führt die JPEG-Komprimierung in Software aus; dieser Wert misst daher nicht den Aufwand für einen Snapshot der App. `android.control.aeAvailableTargetFpsRanges` bietet nur `[15 30]` und `[30 30]`: Es gibt keinen fest auf 15 fps eingestellten Sensormodus. Ein Stream mit 15 fps entsteht daher durch die Taktung des Encoders und nicht durch eine entsprechende Anforderung an den Sensor.

Der Hardware-H.264-Encoder ist `c2.rk.avc.encoder` und wird von der Codec2-HAL bereitgestellt (`android.hardware.media.c2@1.1-service`; auf diesem Panel läuft kein OMX-Prozess `media.codec`). Er führt `OMX.rk.video_encoder.avc` als Alias, sodass eine namensbasierte Auswahl sowohl auf diesem Panel als auch auf dem TPA10 *etwas* findet. Es handelt sich jedoch um unterschiedliche Komponenten auf entgegengesetzten Seiten des Übergangs von OMX zu Codec2; ein gleiches Verhalten darf nicht vorausgesetzt werden. Deklariert sind `176x144` bis `4096x2160` mit einer Ausrichtung von `2x2`, ein angegebener Bitratenbereich von 1 bit/s bis 20 Mbit/s und 32 gleichzeitige Instanzen. Anders als das TPA10 besitzt dieses Panel außerdem den Hardware-HEVC-Encoder `c2.rk.hevc.encoder`, den ha-paneld derzeit nicht verwendet.

Ein Panel, das Kamerakarten anzeigt, befindet sich nicht im Leerlauf: Auf dem gemessenen Flotten-Dashboard hielt ha-paneld zwei aktive `c2.rk.avc.decoder`-Instanzen. Eine Encoder-Sitzung konkurriert daher auf derselben Rockchip-VPU mit bereits laufender Decoder-Arbeit.

ha-paneld includes an **experimental camera-serving feature that is off by default**. It is enabled per panel by the **Camera** switch on the Camera card in Configure, which appears because this panel has a camera - here because the device profile declares `hardware.camera`, though a board whose profile says nothing offers the card too whenever Android enumerates a camera (see [enabling the camera on a panel whose profile does not declare one](../../profiles/unofficial/README.md#enabling-the-camera-on-a-panel-whose-profile-does-not-declare-one)), alongside **Resolution**, **Frame rate** and **Bitrate** (720p / 15 fps / 2000 kbps) and an **Exposure** bias in stops for a camera that reads the room darker or brighter than it looks. Those three are what a stream gets when its URL asks for nothing, and a stream URL can override any of them in either direction; they are defaults, not ceilings. Several viewers share one encode session, bound by the first one to connect, so a second viewer costs packetisation and network rather than a second encode. With the switch on it serves a video-only H.264 stream at `rtsp://<panel>:8554/live` and a still at `GET /api/v1/camera/snapshot.jpg`. Enabling the switch from Home Assistant asks for approval on the panel first, in every security mode. The RTSP URL is intended for Home Assistant Generic Camera, go2rtc and Frigate ingestion. Whenever the camera is open the panel draws its own red indicator that page content cannot cover, and if that indicator cannot be drawn the camera does not open. It flashes about once a second when the camera opens and backs off over a couple of minutes to a flash about once a minute; the half-second flash never gets shorter or fades away, settling at 62% opacity as it becomes rarer. A new stream, a recovery after a fault or the screen coming back on returns it to a flash every second, and no setting turns it off or changes the schedule. See [`GET /api/v1/status`](../../api.md) for the `camera` object that reports the encoder, the delivered frame rate and bitrate, and any fault.

> [!WARNING]
> Do not put a Home Assistant camera card for **this** panel on **this** panel's own dashboard. The panel would decode its own encode in a loop, on the same video engine, for no benefit.


## NFC — vorhanden, aber nicht in Android eingebunden

An **NXP NFC controller** is bound at `i2c-7 0x28` (`nxpnfc` driver) with a `/dev/nxpnfc` node (`crw------- root root`), yet `pm list features` does **not** report `android.hardware.nfc` — the Android NFC service/HAL is not enabled in this firmware. So the silicon exists but is inert to apps as shipped; using it would require an NFC HAL + the NfcService, or talking to `/dev/nxpnfc` directly as root. Present but unused by ha-paneld.

## Zugriffsmodell im Überblick

- **LED**: app-direct (`/dev/ledjni`) — no root, no daemon.
- **IMU**: direkt aus der App (`SensorManager`).
- **NFC**: present (NXP) but Android-NFC disabled; root-only as shipped.
- **Navigation**: Androids eigene Navigationsleiste über den profilgesteuerten Modus `Native`.
- **Bildschirmhelligkeit / Ruhezustand / Navigation / TTS**: Android-Standardwege (wie auf jedem Panel).
