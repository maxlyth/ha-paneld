# Electron WF1589T (Rockchip rk3576)

The high-end panel of the set: a **10.1" 1920×1200 (~226 ppi)** rk3576 unit with **4 GB RAM**, an **app-direct RGB LED** (no root needed), a 6-axis IMU and **Google Play services** so WebView and apps update themselves. Its firmware also provides Android's own navigation bar. NFC silicon is present but inert. Reverse-engineered on a live unit (Android 14 userdebug, `adb root`).

> [!TIP]
> Most-needed facts: `userdebug` so **`adb root` just works**; the LED is the one panel that needs **no root path** (`/dev/ledjni`, world-rwx); **GMS/Play present** so **no WebView sideload** is needed; the bundled profile offers **Native navbar** mode; stock UI is **physically tiny** until you [raise the display density](#display-density--raise-it).

| | |
|---|---|
| SoC | Rockchip **rk3576** (`ro.board.platform=rk3576`, `ro.product.device=WF1589T`) |
| Display | **1920×1200** (16:10), ~10.1" / **~226 physical ppi**, 60 Hz. Android factory/base logical density **160 dpi** is independent of physical PPI; raise the logical density for a larger touch UI — see note below |
| Android | 14, **userdebug** (`adb root` available; `su` present) |
| Google services | **GMS / Play Store present** (unlike the PX30 + TPA10) — so WebView and apps update via Play; no WebView sideload needed |
| ABI | arm64-v8a |
| Navigation | Android's own Back, Home and Recents bar; the bundled profile enables ha-paneld's `Native` navbar mode |
| Radios | Wi-Fi (+ direct/passpoint), Bluetooth + BLE. **No zigbee, no IR, no cellular.** |

> [!TIP]
> Changing firmware on a button-less panel? Read [Firmware backup & restore](../firmware-backup-restore.md) first — the WF1589T (rk3576, Android 14, 58.24 GB eMMC `mmcblk1`, updater `com.elclcd.otaupdater`) uses `adb reboot loader` + `rkdeveloptool`; its maskrom test-point is not yet located.

## Gaining adb + root access

The WF1589T ships as a `userdebug` build with Google Play, so `adb root` works directly and `su` is present — no password, no backdoor. The LED is app-direct (below), so root is rarely needed at all.

```bash
adb root                     # userdebug → root adbd shell
adb shell su 0 id            # uid=0 → root confirmed
```

> [!CAUTION]
> The WF1589T has an OTA updater (`com.elclcd.otaupdater`) that can revert your changes. If you've enabled adb, disable it (reversible): `adb shell pm disable-user --user 0 com.elclcd.otaupdater`. See [Stop unwanted updates](../firmware-backup-restore.md#stop-unwanted-updates).

## WebView — already handled by Play

The WF1589T has **Google Play**, so unlike the PX30 + TPA10 you don't sideload a WebView: update *Android System WebView* from the Play Store (or the Play WebView dev channel) and you're current. See [Updating the system WebView](README.md#updating-the-system-webview) for the cross-panel picture.

## Native Android navbar

The WF1589T firmware draws its own Back, Home and Recents bar. Its bundled profile therefore offers `Native` navbar mode, which leaves those controls to Android and draws no ha-paneld overlay or reveal strip. The capability is profile-gated rather than tied to this model in code. Other panel profiles can declare it after their firmware's navbar has been verified. Fullscreen renderer settings and Android dashboard lock can still hide the system bar.

## Display density — raise it

At the factory/base logical density (160 dpi), Android renders at roughly 1 dp ≈ 1 px, so buttons, text and dashboard cards come out **physically tiny and hard to touch**. The base value is Android's layout reset reference, not the panel's ~226 physical PPI. ha-paneld's **HA-optimised** preset uses 212 dpi as the verified starting point; adjust it to taste for your room and dashboard:

```sh
adb shell wm density 212        # ha-paneld starting point; `wm density reset` restores the 160-dpi base
```

At 212 dpi the effective canvas is approximately 1449×906 dp. Raising the value makes the touch UI larger and shows less dashboard content; lowering it does the reverse.

## LED — `/dev/ledjni` (app-direct, no root)

`/sys/class/leds` has no RGB node (only `mmc1::`). The front RGB LED is driven through a character device that is world-rwx and labelled `device` (app-accessible under SELinux), so a normal app drives it **without root or a helper daemon**. This is the one panel class where the LED needs no root path.

ha-paneld uses this via `Rk3576LedController` (the LED entity is published only where `/dev/ledjni` opens).

The factory `com.gulukai.pwmlightdemo` package also opens this device. Its boot-started foreground service continuously cycles the LED through seven colours, overwriting commands from ha-paneld and making Home Assistant's last commanded state differ from the physical LED. The device protocol has no state read-back, so two applications cannot share truthful control. The WF1589T profile therefore marks this demo as recommended in the **Vendor packages** UI, where disabling it remains a deliberate reversible action.

<details>
<summary>`/dev/ledjni` node + ioctl protocol</summary>

```text
/dev/ledjni   crwxrwxrwx  system system  u:object_r:device:s0
```

The ioctl protocol (clean-room reverse-engineered from the vendor sample, no vendor blob bundled — see [`app/src/main/cpp/led_jni.c`](../../app/src/main/cpp/led_jni.c)):

```c
int fd = open("/dev/ledjni", O_RDONLY | O_NOCTTY);
ioctl(fd, 0xa1, R);   // red,   0..15
ioctl(fd, 0xa2, G);   // green, 0..15
ioctl(fd, 0xa3, B);   // blue,  0..15
ioctl(fd, 0x99, 0);   // off
close(fd);
```

</details>

## Sensors — 6-axis IMU (via Android `SensorManager`)

Unusually for a wall panel, the WF1589T exposes a full motion suite through standard `SensorManager` (no root): `accelerometer`, `gyroscope`, `gravity`, `linear_acceleration`, `game_rotation_vector`. Backing chips: Kionix **KXTJ9** + Bosch **BMA2xx** (accel). No `TYPE_LIGHT`/`TYPE_PROXIMITY` is exposed (none fitted).

No ambient-light, proximity, temperature or humidity sensor is bound on this board (contrast the [TPA10](tpa10.md), which has all four). Presence sensing here is motion-only, via the IMU.

## Camera

GalaxyCore **GC05A2** (i2c `4-0037` in the table above), a 2592x1944 sensor. Android reports one camera at `LIMITED` hardware level, `BACKWARD_COMPATIBLE` only, `Facing: Front`, with no flash and no autofocus, through the `internal/0-1` provider. A second `external/0-0` provider is present with no devices attached, and the panel declares `android.hardware.camera.external`.

1280x720 is offered in all three formats — `IMPLEMENTATION_DEFINED`, `YUV_420_888` and `BLOB`. The HAL advertises a one-frame stall for a 720p `BLOB` capture at 30 fps, but ha-paneld captures `YUV_420_888` and performs software JPEG compression, so that figure does not measure the app's snapshot cost. `android.control.aeAvailableTargetFpsRanges` offers only `[15 30]` and `[30 30]`: there is no locked 15 fps sensor mode, so a 15 fps stream comes from pacing the encoder, not from asking the sensor.

The hardware H.264 encoder is `c2.rk.avc.encoder`, served by the Codec2 HAL (`android.hardware.media.c2@1.1-service`; there is no OMX `media.codec` process on this panel). It carries `OMX.rk.video_encoder.avc` as an alias, so name-based selection finds *something* on both this panel and the TPA10 — but they are different components on opposite sides of the OMX-to-Codec2 transition and should not be assumed to behave alike. It declares `176x144`-`4096x2160` at `2x2` alignment, a bitrate range reported as 1 bps through 20 Mbps, and 32 concurrent instances. Unlike the TPA10 this panel also has a hardware HEVC encoder, `c2.rk.hevc.encoder`, which ha-paneld does not currently use.

A panel showing camera cards is not idle: on the measured fleet dashboard, ha-paneld held two live `c2.rk.avc.decoder` instances, so an encode session contends with existing decode work on the same Rockchip VPU.

ha-paneld includes an **experimental camera-serving feature that is off by default**. It is enabled per panel by the **Camera** switch on the Camera card in Configure, which appears only because this device profile declares `hardware.camera`, alongside **Resolution**, **Frame rate** and **Bitrate** (720p / 15 fps / 2000 kbps). Those three are what a stream gets when its URL asks for nothing; a URL may ask for less and never for more, so they are a default and a ceiling at once. With the switch on, the implementation is intended to serve a video-only H.264 stream at `rtsp://<panel>:8554/live` and a still at `GET /api/v1/camera/snapshot.jpg`; end-to-end acceptance on this panel is still pending. The RTSP URL is intended for Home Assistant Generic Camera, go2rtc and Frigate ingestion. It accepts `?res=`, `?fps=` and `?kbps=` to ask for *less* than the configured ceilings and never for more; the first viewer's choice sets the single encode session and later viewers join it. Whenever the camera is open the panel draws its own red indicator that page content cannot cover, and if that indicator cannot be drawn the camera does not open. See [`GET /api/v1/status`](../api.md) for the `camera` object that reports the encoder, the delivered frame rate and bitrate, and any fault.

> [!WARNING]
> Do not put a Home Assistant camera card for **this** panel on **this** panel's own dashboard. The panel would decode its own encode in a loop, on the same video engine, for no benefit.


## NFC — present but not wired into Android

An **NXP NFC controller** is bound at `i2c-7 0x28` (`nxpnfc` driver) with a `/dev/nxpnfc` node (`crw------- root root`), yet `pm list features` does **not** report `android.hardware.nfc` — the Android NFC service/HAL is not enabled in this firmware. So the silicon exists but is inert to apps as shipped; using it would require an NFC HAL + the NfcService, or talking to `/dev/nxpnfc` directly as root. Present but unused by ha-paneld.

## Access model summary

- **LED**: app-direct (`/dev/ledjni`) — no root, no daemon.
- **IMU**: app-direct (`SensorManager`).
- **NFC**: present (NXP) but Android-NFC disabled; root-only as shipped.
- **Navigation**: Android's own navbar through the profile-gated `Native` mode.
- **Screen brightness / sleep / navigate / TTS**: standard Android paths (as on any panel).
