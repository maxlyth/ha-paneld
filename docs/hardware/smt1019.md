# ZHICAI SMT1019 (Rockchip rk3576)

> [!NOTE]
> The stock-firmware facts come from a reporter's `/diag` dump and the retail listing (GitHub [#8](https://github.com/maxlyth/ha-paneld/issues/8)). The supplier-firmware facts come from a second reporter running that build, with vendor documentation they published in [#106](https://github.com/maxlyth/ha-paneld/issues/106). ha-paneld's own profile has not been validated on either.

A ~10.1" rk3576 wall tablet sold as "Generic SMT1019 / RK3576_64GB" (manufacturer **ZHICAI TECHNOLOGY**), built on an Electron `WF2489T` board — a sibling of the rk3576 [WF1589T](wf1589t.md).

**There are two firmware builds in the wild, and they differ in the one way that matters most.** The retail unit ships a locked-down production build with no root; the supplier will also provide a `userdebug` build, and a reporter reflashed to it. Everything root-gated depends on which one a panel is running, so check before assuming.

| | Stock (production) | Supplier `userdebug` |
|---|---|---|
| Build | `ZX-SMT1019-R157-V1.0A` | `ZX-SMT1019-R157-V2.0-…` (`Apolosign/WF2489T/WF2489T:14/…:userdebug/release-keys`) |
| Root | **none** — `su` absent | **yes** — `adb shell id` is already `uid=0`, and `su` is the **join style** (`su 0 "<cmd>"`; `su -c` answers `su: invalid uid/gid '-c'`, which is a dialect mismatch, *not* absent root) |
| SELinux | **Enforcing** — confines the LED ioctl to privileged domains | Permissive |
| Verified boot | locked | `verified=orange flash=unlocked`, `/system` still read-only behind **dm-verity** |
| RGB LED | `/dev/ledjni` opens `O_RDONLY` but the **ioctl is denied** to sandboxed apps (`EACCES` / `rc=-13`); no app-side path | Driven by the root helper — reported working |

Shared by both: Rockchip **rk3576** (`ro.product.device=WF2489T`), **1280×800** ~10.1" display, ~4 GB / 64 GB, Android **14**, `arm64-v8a`, no Google Play. Retail: [Amazon B0GSWXPB9K](https://www.amazon.com/dp/B0GSWXPB9K).

### Installing on the `userdebug` build

`/system` stays read-only behind dm-verity even though the panel is rooted, so the helper has nowhere boot-persistent to live and provisioning stops. One host-side sequence clears it — it **reboots the panel**, so do it with the panel in front of you:

```bash
adb -s <ip>:5555 root && adb -s <ip>:5555 disable-verity && adb -s <ip>:5555 reboot
# once it is back:
adb -s <ip>:5555 root && adb -s <ip>:5555 remount
```

Provisioning then completes and the helper survives reboots (reporter-confirmed, [#106](https://github.com/maxlyth/ha-paneld/issues/106)).

### Sensors and I/O the board exposes

Recorded so the work does not start from guesswork. Temperature and humidity are now enabled (below); the rest is not yet wired. The vendor's own documentation states that **temperature and humidity are read from `getevent`** — plain evdev input devices, not an i2c driver — and that the event *index* differs between variants with and without a light sensor, so match on the device **name** rather than the number. Values arrive as raw integers whose scaling the vendor leaves to the caller, so a reading has to be calibrated against the vendor's own display once.

| Function | Where it appears |
|---|---|
| Temperature / humidity | evdev `sun-ths`, `sun-hum` (i2c `0-0044:gxht30`) — **now enabled**, see below |
| Proximity / time-of-flight | `/dev/vi530x` (i2c `4-006c`) — **now enabled**, see below. It stays **silent until started** over ioctls, so watching its input node alone yields nothing |
| Ambient light | evdev `lightsensor-level` (i2c `4-0048:ls_stk3x1x`) |
| RGB LED | `/dev/ledjni` |
| Two GPIO lines | `/dev/gpio_control` |

## ha-paneld support

The bundled [`smt1019.yaml`](../../app/src/main/assets/device-profiles/smt1019.yaml) profile gives its tightly scoped `wf2489` device-substring branch priority over the WF1589T profile's broader `rk3576_u` model branch, so the observed `WF2489T` unit does not collide with the other rk3576 family. It declares:

- **`hardware.led.mechanism: rk3576-ioctl-daemon`** — the compiled ioctl driver is routed only through the authenticated root helper. Its live check keeps the LED unavailable and unpublished when that helper cannot drive the node, as on the reported no-`su` installation.
- **`platform.su_form: none`** — no app-accessible `su`, so root-gated features (evdev buttons, CPU governors, the `bl_power` screen-off path) are unavailable on the reported firmware.
- **`hardware.screen_off: brightness-zero`** — the no-root screen-off path.

Standard-Android capabilities (brightness, sleep, navigate, TTS, MQTT auto-discovery) work; the LED and hardware buttons do not on the reported installation. The vendor's own RGB control works because that app runs system-privileged; ha-paneld would need a working root/helper path or a firmware change to reach the same ioctl.

**Proximity is enabled.** The board's VI530x time-of-flight sensor is now a proximity source. It is unlike every other sensor ha-paneld reads: the driver reports nothing at all until userspace starts it, so the helper issues the vendor's own power-on, initialise, period and start sequence and then reads each measurement back with the driver's own single-call read. Distances are handed to the same learning that every proximity source feeds — ha-paneld works out which direction means *near* and at what level by watching your panel, so nothing here depends on a threshold guessed in advance. It needs the root helper. **This has not been run on hardware yet**: the sequence and the record layout come from the vendor's own driver sources, and the first panel to run it is telling us something either way — please report what you see on [issue #106](https://github.com/maxlyth/ha-paneld/issues/106).

**Room temperature and humidity are enabled.** The board carries the same GXHT30 part and vendor evdev layout as the [ZX-SMT156](zx-smt156.md), whose profile already uses this route, so `sensors.cht8305` is now `true` here too. A verified root helper or approved Shizuku shell point-reads `sun-ths` and `sun-hum`; the default-enabled Room entities publish no value when neither authority is available. **The inherited scale has not been checked against this vendor's display.** Compare both readings with the vendor `smt-test` app and report them in [#106](https://github.com/maxlyth/ha-paneld/issues/106). `sensors.room_temp_offset_c` can compensate only a constant temperature bias; multiplicative scaling and humidity still require validation.

> [!IMPORTANT]
> **The profile otherwise describes the stock build, so a panel on the supplier `userdebug` build is still under-served.** `su_form: none` and `app_can_su: false` were written from the no-root unit and are wrong there — the panel has root, and ha-paneld will not use it, which also keeps the in-app helper install switched off. Correcting this needs a firmware-aware variant match plus a check on real hardware that the app's `su` reaches `uid=0`, since a profile that claims root where there is none is worse than one that claims too little. Tracked in [#106](https://github.com/maxlyth/ha-paneld/issues/106); the standalone `helper/install-daemon.sh` route works on that build today.

## WebView

The SMT1019 runs Android 14 with **no Google Play** (no GMS was detected), so the system WebView does not auto-update through Play. On the supplier `userdebug` build a panel was observed running `com.google.android.webview` **124.0.6367.179**, which is old enough to matter. The stock production build (`ZX-SMT1019-R157-V1.0A, 2026-02-05`) has not been established — the full ROM is a block-format OTA and extracting individual APKs requires a full `sdat2img` pipeline. If the stock build is old, a manual arm64 (`arm64-v8a`) SystemWebView sideload will be needed — the same class of fix as the NSPanel Pro/TPA10. If you have an SMT1019, run `adb shell dumpsys webviewupdate | grep "Current WebView"` on the stock firmware and report the version in [#8](https://github.com/maxlyth/ha-paneld/issues/8).
