# ZHICAI SMT1019 (Rockchip rk3576)

> [!NOTE]
> The stock-firmware facts come from a reporter's `/diag` dump and the retail listing (GitHub [#8](https://github.com/maxlyth/ha-paneld/issues/8)). The supplier-firmware facts come from a second reporter running that build, with vendor documentation they published in [#106](https://github.com/maxlyth/ha-paneld/issues/106). Reporter evidence confirms the supplier build's root route, boot-persistent helper and raw climate axes. The bundled profile has not yet been validated end to end. Climate accuracy and the VI530x proximity route still need hardware tests.

A ~10.1" rk3576 wall tablet sold as "Generic SMT1019 / RK3576_64GB" (manufacturer **ZHICAI TECHNOLOGY**), built on an Electron `WF2489T` board — a sibling of the rk3576 [WF1589T](wf1589t.md).

**There are two firmware builds in the wild, and they differ in the one way that matters most.** The retail unit ships a locked-down production build with no root; the supplier will also provide a `userdebug` build, and a reporter reflashed to it. Everything root-gated depends on which one a panel is running, so check before assuming.

| | Stock (production) | Supplier `userdebug` |
|---|---|---|
| Build | `ZX-SMT1019-R157-V1.0A` | `ZX-SMT1019-R157-V2.0-…` (`Apolosign/WF2489T/WF2489T:14/…:userdebug/release-keys`) |
| Root | **none** — `su` absent | **yes** — `adb shell id` is already `uid=0`, and the app's `su 0 sh -c "<cmd>"` form is hardware-confirmed with quoting intact; `su -c` answers `su: invalid uid/gid '-c'`, which is a dialect mismatch, *not* absent root |
| SELinux | **Enforcing** — confines the LED ioctl to privileged domains | Permissive |
| Verified boot | locked | `verified=orange flash=unlocked`; `/system` was observed read-only, with writable-overlay and dm-verity state not yet distinguished |
| RGB LED | `/dev/ledjni` opens `O_RDONLY` but the **ioctl is denied** to sandboxed apps (`EACCES` / `rc=-13`); no app-side path | Driven by the root helper — reported working |
| Full screen-off | Brightness-zero fallback without a helper | The profile routes `bl_power` through the authenticated helper; an SMT1019 end-to-end result has not yet been reported |

Shared by both: Rockchip **rk3576** (`ro.product.device=WF2489T`), **1280×800** ~10.1" display, ~4 GB / 64 GB, Android **14**, `arm64-v8a`, no Google Play. Retail: [Amazon B0GSWXPB9K](https://www.amazon.com/dp/B0GSWXPB9K).

### Installing on the `userdebug` build

`/system` reads as read-only even though the panel is rooted — either because a writable overlay is not mounted, or because dm-verity is on — so the helper has nowhere boot-persistent to live and provisioning stops. Try the reboot-free remount first; only the fallback reboots the panel, and a reboot needs you in front of it because a PIN-protected panel cannot start its apps again until the PIN is entered:

```bash
# Try this first — no reboot, and on a panel that already carries a scratch overlay it is the whole fix:
adb -s <ip>:5555 root && adb -s <ip>:5555 remount

# Only if that is refused. This REBOOTS the panel, so be in front of it and unlock any PIN afterwards:
adb -s <ip>:5555 disable-verity && adb -s <ip>:5555 reboot
adb -s <ip>:5555 root && adb -s <ip>:5555 remount
```

Provisioning then completes and the helper survives reboots (reporter-confirmed, [#106](https://github.com/maxlyth/ha-paneld/issues/106)).

### Sensors and I/O the board exposes

Recorded so the work does not start from guesswork. Temperature, humidity and proximity are enabled below; ambient light and the two GPIO lines are not yet wired. The vendor's own documentation states that **temperature and humidity are read from `getevent`** — plain evdev input devices, not an i2c driver — and that the event *index* differs between variants with and without a light sensor, so match on the device **name** rather than the number. Hardware evidence confirms the raw climate encoding is in hundredths; physical accuracy still needs comparison with the vendor display or a reference sensor.

| Function | Where it appears |
|---|---|
| Temperature / humidity | evdev `sun-ths`, `sun-hum` (i2c `0-0044:gxht30`). **Enabled:** the raw hundredths encoding is confirmed, but physical accuracy is not |
| Proximity / time-of-flight | `/dev/vi530x` (i2c `4-006c`). **Experimental:** the driver axes are confirmed, but ha-paneld's complete startup and read path has not run on hardware. Distance is `ABS_HAT1X` in **millimetres** and reading validity is `ABS_WHEEL` |
| Ambient light | evdev `lightsensor-level` (i2c `4-0048:ls_stk3x1x`) |
| RGB LED | `/dev/ledjni` |
| Two GPIO lines | `/dev/gpio_control` |

## ha-paneld support

The bundled [`smt1019.yaml`](../../app/src/main/assets/device-profiles/smt1019.yaml) profile gives its tightly scoped `wf2489` device-substring branch priority over the WF1589T profile's broader `rk3576_u` model branch, so the observed `WF2489T` unit does not collide with the other rk3576 family. It declares:

- **`hardware.led.mechanism: rk3576-ioctl-daemon`** — the compiled ioctl driver is routed only through the authenticated root helper. Its live check keeps the LED unavailable and unpublished when that helper cannot drive the node, as on the reported no-`su` installation.
- **`platform.su_form: none`** — no app-accessible `su`, so root-gated features (evdev buttons, CPU governors, the `bl_power` screen-off path) are unavailable on the reported firmware.
- **`hardware.screen_off: daemon-blpower`**: the profile uses the authenticated helper to power the backlight down through `bl_power`. This is full screen-off and lets the renderer stop drawing behind it. `ScreenController` falls through daemon → direct root → brightness-zero at runtime. Stock firmware with neither the helper nor direct root keeps its previous brightness-zero behaviour; a helper-less rooted build can use direct root. Declaring the capable route costs the stock configuration one refused socket connection per screen-off. The route is included in the bundled profile, but an SMT1019 end-to-end result has not yet been reported.

Standard Android capabilities such as brightness, navigation, TTS and MQTT auto-discovery work on either build. The stock no-`su` installation cannot drive the LED or root-only hardware. The supplier build can use the authenticated helper, and its LED control has been reported working. No hardware buttons have been identified.

**Proximity is experimental.** The VI530x driver reports nothing until userspace starts it, so the helper follows the vendor's power-on, initialise, period and start sequence before reading a measurement. Reporter evidence confirms that `ABS_HAT1X` is distance in millimetres and `ABS_WHEEL` reports whether the reading is valid. A raw value of 1896 therefore means about 1.9 m. ha-paneld feeds the unscaled distance into the same adaptive learning used by its other proximity sources, so it does not depend on a guessed threshold or polarity. The helper's complete ioctl startup and read path has not yet run on hardware. Please report the result on [issue #106](https://github.com/maxlyth/ha-paneld/issues/106).

**Room temperature and humidity are enabled.** A verified root helper or approved Shizuku shell reads the GXHT30's `sun-ths` and `sun-hum` input devices. The default-enabled Room entities publish no value when neither route is available. Reporter evidence confirms the raw encoding on this hardware ([#106](https://github.com/maxlyth/ha-paneld/issues/106), 2026-08-14): `sun-ths` uses `ABS_THROTTLE` with bounds of -4000..12500, while `sun-hum` uses axis `0x1d` with bounds of 0..10000. A live panel reported 2479 and 5704. These values are consistent with hundredths of a degree Celsius and hundredths of a percent, but they do **not** establish physical accuracy. Compare them with the vendor display or a reference sensor before relying on them. `sensors.room_temp_offset_c` can correct a constant temperature bias from the panel's own warmth; it cannot correct multiplicative scaling or humidity calibration.

> [!IMPORTANT]
> **The profile's root hints still describe the stock build, but they no longer veto the bundled helper.** `su_form: none` and `app_can_su: false` remain correct for the retail firmware. When the exact bundled helper is needed, ha-paneld now observes live root instead of treating those hints as proof: the supplier build's shipped `su 0 sh -c "<cmd>"` form reached `uid=0` twice with quoting intact, so the app can install its release-matched helper there without writing `/system`. A stock panel simply fails that live probe and remains unchanged. The standalone boot-persistent helper route is separate and still needs the remount/verity procedure above.

## WebView

The SMT1019 runs Android 14 with **no Google Play** (no GMS was detected), so the system WebView does not auto-update through Play. On the supplier `userdebug` build a panel was observed running `com.google.android.webview` **124.0.6367.179**, which is old enough to matter. The stock production build (`ZX-SMT1019-R157-V1.0A, 2026-02-05`) has not been established — the full ROM is a block-format OTA and extracting individual APKs requires a full `sdat2img` pipeline. If the stock build is old, a manual arm64 (`arm64-v8a`) SystemWebView sideload will be needed — the same class of fix as the NSPanel Pro/TPA10. If you have an SMT1019, run `adb shell dumpsys webviewupdate | grep "Current WebView"` on the stock firmware and report the version in [#8](https://github.com/maxlyth/ha-paneld/issues/8).
